# 设计可阅读、可维护的业务流程图

在新建业务图、调整图的范围或层次、处理读者看不懂的图，以及判断业务更新应改哪些图时读取本指南。

总览和细图统一使用业务流程图。每层都要能从入口沿真实动作、条件和交接走到结果；分类目录与无连接的业务卡片不能代替总览。

软件提供图的表达、渲染、交互和结构检查。AI 根据当前业务资料判断业务边界、图的范围、阅读层次、表达方式和修改范围。节点数量、图的深度和排布方向都服务于具体内容与读者的任务。

先按[业务边界](boundary-design.md)核实谁拥有结果、规则和生命周期，再组织阅读。文件字段和 CLI 命令以当前安装版本的[编写约定](map-authoring.md)为准。AI 显式编写总览流程，使用步骤的 `concept` 引用场景的自有流程形成下层；`part_of` 只表示业务归属，不推断执行顺序。需要新增文件结构时按项目授权确认后实施。

## 1. 明确读者正在判断什么

从用户请求、已有图和业务资料确定这次阅读的目的。例如：

- 系统为客户完成哪些事情，这些业务怎样协作？
- 用户启动监控后，会经过哪些环节，得到什么结果？
- 读到一页帖子后，什么条件让这条路线继续或结束？

把当前实现、已经确认的业务要求、候选变化和用途解释分别表明依据。业务目的从决定或场景证据取得；源码说明当前做法。会改变图中结果的资料缺口，保留明确的待核实状态。

## 2. 分块调查并持续修正已画流程

首次建图或从零重建时，把图当作持续修正的外部工作记忆。无需先看完整仓库：选择当前能核实的一条用户路径、规则或生命周期，读相关入口、决定性方法及必要使用方，建立有来源的局部闭环。

### 从一个有证据的分块继续

1. 明确当前要查的入口、结果和疑问，读取足以证实该路径的源码与规则，不先收集所有目录。
2. 当证据已支持一条可理解的路径，及时把动作、关键条件、结果和符号锚点写入流程文件，再继续下一块。只画已经核实的内容；外部交接到当前证据边界为止，未知内部过程留作调查缺口。
3. 保存后核对局部业务含义及已有文件之间的引用。小范围校验帮助发现断链，不能代替继续调查，也不意味着整个业务已覆盖。
4. 下一块优先处理会改变当前理解的未知：例如同一状态的其他写入方、回调、恢复入口、退出路径或跨业务消费者。根据新证据回看已画流程，再决定继续深入还是转向另一项指定业务。

分块以业务证据与理解范围决定，不固定文件数、节点数、层数或调查轮数。需要更多资料才能证实一个条件时先补关键证据；已有局部路径足以写清时，不因仓库其余部分未读而延迟落图。

### 新证据要改回已画部分

新读到的事实否定了原来的顺序、条件、归属或生命周期时，立即修改、删除或重构原图，不能只追加一个新节点或备注保留相互矛盾的旧解释。必要时拆分或合并流程，修正共享概念、子流程引用、上层摘要、业务备注与锚点，再核对受影响的来路和结果。

例如先看到“订单创建后调用发货”，随后发现发货由支付成功事件触发，应改回已画的总览和发货入口，而不是在旧的串行路径旁再追加一条支付事件线。现有方法名或图上的旧结论不能替代调用、状态和运行证据。

发现跨业务关系时，核实交接两端的真实契约，回头调整已经画出的所有者、输入输出和连接。未读的另一端不能被描述为已核实内部流程；先表达已证实的边界，并保留明确的下一处调查入口。

### 用文件保存进展与恢复上下文

长任务在目标项目的 `tmp/` 中维护带日期和主题的状态文件；已有合适记录时直接更新。保存用户范围、当前结论及证据位置、已写概念／流程、未覆盖业务、影响结论的疑问，以及下一步要打开的具体入口。确认事实、暂定理解与未知分开写，避免把“看过文件”当成覆盖完成。

业务流程和锚点保存可复用的已核实知识，状态文件保存当前调查进度与待核实项；不向业务 UI 加入调查过程或 AI 编排理由。重要分块落盘或理解重构后更新状态。上下文恢复时，先读状态，再核对当前 Git 差异、已画流程和下一处决定性源码；不依赖上一段对话的记忆继续推断。

当指定范围的入口、重要分支、状态变化、退出与恢复路径已有证据支持，协作边界可解释，且相关图已经消除旧误解时，完成整体校验和实际阅读后交付。尚未调查或缺证据的部分单独报告；不把局部合法图宣称为整个系统的完成图，也不为凑齐固定层级扩画无关内容。

## 3. 分别判断业务边界与图的边界

业务边界由结果承诺、规则与状态的所有权、完整生命周期和协作契约决定。一张图的边界由读者这次需要理解的范围决定。

同一条客户旅程可以跨多个业务所有者；一个业务也可以用多张图解释。保留共享概念的稳定编号与资料，让各图引用对应业务；参与一张流程图只表达协作，业务归属继续由所有权决定。

在选择本层节点前，明确：

| 问题 | 对画图的作用 |
| --- | --- |
| 从什么场景开始，到什么结果结束？ | 决定本图起点、终点和主要路径 |
| 这一层读者需要作什么判断？ | 决定粒度与关键条件 |
| 哪些协作者需要出现，怎样交接？ | 决定图的外部边界与必要引用 |
| 哪些细节适合继续深入？ | 决定下一层要解释的内容 |

图的范围和层次由 AI 在编写时判断，界面不展示 AI 安排图的理由。业务规则自身的目的和取舍写入相应节点的备注；局部修改沿用仍然成立的边界。

## 4. 根据理解成本安排层次

总览先建立主要业务、关键交接和结果的联系，具体环节再展开其规则。AI 依据实际内容决定层数：简单业务可以在一层读完，复杂业务可以逐层深入。

“一层围绕一个问题”是组织方法。紧密相关、共同解释同一结果的问题可以放在一起。判断是否拆图时，检查：

- 当前画面是否同时要求读者理解多种粒度或几条独立业务？
- 一个节点是否需要塞入多个动作、判断和例外才能说清？
- 连线交叉或长篇文字是否掩盖了主要路径？
- 某个环节是否有独立、可命名的详细问题，值得未来单独进入？

需要拆分时，在上层保留这一步做什么、改变结果的重要条件、产物和详细内容入口；下一层从这个环节的真实输入展开到它承诺的结果。当前 Viewer 只展示显式流程；流程步骤通过概念引用连接场景自己的细图。上层与下层分别交代真实业务路径，保持业务归属真实，不为导航修改所有权。

避免仅按技术目录、接口个数、节点数量或固定层数切图。读者能顺着主线理解并找到完整分支，是粒度是否合适的依据。

## 5. 写清每条流程连接

使用动作、判断与结果表达流程，必要的业务交接放在相应步骤和条件中。连线表示执行顺序或条件后续；业务归属、资料分类和依赖保留在概念资料中，不冒充流程连接。

串联箭头表达真实先后；并行路径分别交代触发和汇合；循环写清回到哪一步。选用当前格式能准确表达的结构，涉及新的并行或导航语义时先确定产品契约。

每个动作框表达一个可理解的动作；判断框表达一个能作答的问题。复杂条件拆开后，核对“全部满足”或“任意一项满足”的关系仍然等价。分别检查：

| 判断要素 | 要写清的内容 |
| --- | --- |
| 对象和范围 | 当前判断一条记录、一个账号、一条来源路线，还是整轮任务 |
| 成立条件 | 全部或任意条件；等于边界、信息待定分别怎样处理 |
| 生效时点 | 保存前判断，还是接收整页后控制下一次请求 |
| 结果与后续 | 继续哪一步、停止哪个对象、已有数据怎样保留或处理 |

例如两个上限共同控制采集，应写“条数或页数任意一项达到上限后结束本路线”，并交代计数范围和当前页的处理。“继续”“完成”“去重”等词需要具体对象：写“读取这个接口的下一页”“结束本路线”“平台名称和帖子 ID 相同，沿用已有记录”。

数量、时间、缓存、资格、权限、失败和恢复规则，只在影响当前业务结果时进入本图。细节分别说明单位、计算范围、生效时点、接受的取舍与证据。

## 6. 让人能评价规则的合理性

动作和判断说明发生什么；相邻说明交代为什么：

- **业务目的**：谁需要这条规则，它帮助取得什么结果。
- **接受的代价**：在成本、覆盖、新鲜度、失败恢复上作出的取舍。
- **依据与状态**：已经记录的决定、当前实现、接口能力或有事实支持的解释。

上层保留影响结果的重要取舍，详细依据放相邻说明或更细的图。多个独立判断分别对应各自理由，避免用一段笼统背景解释整张图。

采用读者使用的业务名和完整动作。一个平台类别、编号或术语容易混淆时，在第一次出现处写清含义。长篇内容先检查是否属于当前层，再决定移动说明、拆判断或安排细图。

## 7. 按业务影响决定修改范围

先核实业务变化，再在代码所在分支同步它影响的图、摘要、引用和来源。沿用仍准确的概念身份与表达，围绕必要变化整理完整结果；无需为旧格式兼容保留已经妨碍表达的结构。

| 变化 | 通常需要检查与调整的范围 |
| --- | --- |
| 内部代码移动，业务含义保持 | 相应源码引用；图的业务结构可以保持 |
| 一条内部规则或条件变化 | 所属细图、规则说明，以及提到该条件的摘要 |
| 入口、产物、重要分支或协作契约变化 | 该流程、引用它的上层节点和相关协作者 |
| 业务所有权或生命周期变化 | 重新检查相关边界，按需拆分、合并或重组多张图并更新引用 |
| 仅有表达或阅读问题 | 调整节点用语、布局和阅读路径，保持已确认业务含义 |

例如把某个内部数量上限改为另一个值，先更新对应规则与直接提到它的说明；首次启动开始支持另一类结果时，需要同时检查上层承诺和进入路径。软件文件变化多寡只提供线索，业务影响决定图的改动半径。代码与对应图一起审阅、提交和合入，不把图更新默认留到主分支之后。

合并或重放后，按最终代码重走受影响路径，并核对两边规则叠加后的结果；条件、顺序、子流程引用、备注和上层承诺都可能需要调整。文字无冲突或两段 YAML 都保留下来，不证明合并后的业务自洽。

## 8. 从读者路径验收

先核业务含义，再检查结构，最后查看实际渲染：

1. 从当前支持的总览或入口找到目标业务，确认当前范围和外部交接容易理解。
2. 走正常路径及关键分支，找到清楚的结果、继续或停止对象。
3. 找到数量、时间、权限和失败规则的具体作用范围，以及主要取舍和依据。
4. 通过角标进入子流程并返回，检查上下层承诺一致；有业务备注时点击正文查看，备注详情不承担进入操作。
5. 核对共享概念、节点引用和来源保持一致；完整差异只包含本轮业务影响。
6. 在实际阅读比例下检查文字、连线、条件标签和说明，按影响调整表达或层次。

结构检查证明文件和引用有效，读者路径与业务证据证明图是否讲清楚。完成当前请求的业务范围和阅读结果后交付。
