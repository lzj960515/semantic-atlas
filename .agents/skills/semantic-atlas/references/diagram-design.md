# 按业务组织可讲解的流程图

在新建、重画或重组业务图，以及读者看不懂现有图时读取本指南。软件提供文件、管理、搜索、渲染和导航能力；AI 根据业务证据决定画什么、怎样连接、哪些内容放在一起。这里提供判断方法，不规定业务模板、图数、层数或固定节点。

一组业务图可以从多张平级图开始。项目是资料的保存和查询范围，不天然是一个完整业务，也不要求有一张覆盖全部功能的“业务全貌”图。先确定要讲的业务，再确定每张图的范围和必要的深入入口。

业务责任按[业务边界](boundary-design.md)核实，文件和工具按[编写约定](map-authoring.md)使用。归属、共享资料和源码位置帮助调查，不自动产生流程箭头或父子图。

## 1. 从读者要理解的业务开始

明确本次要让读者理解什么业务、作出什么判断，以及哪些事实会影响判断。结合用户请求、当前源码、相关产品决定和必要运行证据，核实谁做什么、对象怎样变化、什么条件改变路径、结果交给谁使用。

使用具体业务语言。宏观节点可以概括复杂动作，但读者仍应知道发生了什么。例如“顾客下单并付款 → 仓库按订单发货”可以讲业务；“业务触发 → 选择结果 → 返回处理结果”只是一副任意请求都能套用的架子。接收、判断、返回可以是实际业务，写出它们接收什么、按什么判断、改变什么结果。

把当前实现、已经确认的业务要求、用途解释和资料缺口分清。会改变结论的未知先核实；没有依据的业务原因或使用方不写成事实。

## 2. 分块调查并持续修正已画流程

图是可持续修正的外部记忆。首次建图或重建时，从当前能核实的一条用户路径、规则或生命周期开始，读取入口、决定性方法和必要使用方；已有足够证据就及时保存，不等读完全部仓库。

1. 写下当前已经核实的动作、关键条件、结果与源码锚点，核对局部引用。
2. 继续调查会改变这段理解的其他写入方、回调、恢复入口、退出路径或消费者。
3. 新证据否定原来的条件、顺序、归属或边界时，立即修改、删除或重组已画内容，同时检查受影响的摘要、图间引用和备注。不能只追加新节点保留旧误解。
4. 按业务理解继续下一块。分块大小由证据与业务决定，不固定文件数、调查轮数或节点数。

例如先读到“创建订单后调用发货”，后来确认发货由支付成功事件触发，应改回已有路径和发货入口，不能保留原串行关系再加一条支付线。

长任务在所属项目 `tmp/` 保留目标、确认事实、待核实范围、已改流程与下一处源码入口。重要分块或理解变化后更新；恢复上下文先读状态和当前差异。稳定业务知识留在图与所属文档，调查过程不进入业务 UI。

## 3. 分别确定业务边界和图的边界

业务边界由结果承诺、规则和状态的所有权及生命周期决定。图的边界由需要一起理解的业务内容决定，两者不必一一对应：一条客户旅程可以跨多个所有者，一个复杂业务也可以有多张图。

先判断哪些内容共同说明一个业务目标、业务对象或生命周期，以及它们之间有什么真实联系。关联的配置、运行、结果使用和恢复不能仅因分在不同方法、模块或仓库，就画成互不相关的接口碎片。

再检查被放在一起的内容是否有共同的讲解任务。若讲完其中一段就需要切换到另一项独立业务，其余部分对理解前一段没有作用，可以分别成图，放在同一层选择。它们同属一个项目、都使用 AI、共享账号或公共资料，不构成合为一张图的理由。

业务缺少入口、事件或结果使用方时，按缺口继续找证据。缺用户操作就查前端，缺触发就查事件生产者，缺产物去向就查消费者。可访问的相关项目继续调查；第三方内部或不可访问部分保留已知契约和具体缺口，不在仓库边界截断已能查明的业务。

## 4. 根据理解成本安排层次

### 平级图各自讲清业务

独立业务可以各有一张或几张完整图，直接作为顶层入口。顶层不是必须汇总全部图的父图；默认打开其中一张，只是阅读器的初始选择，不要求该图代表全项目。

项目级整理要检查这组图是否覆盖指定范围，以及每张图是否能讲清它声称的业务。读者可以选择相关业务开始，无需先经过统一封面。只有实际业务存在适合一起讲的更大过程时，才编写相应总览；它和其他图一样，范围由内容决定。

### 同一业务保留必要主线

对已经选定的业务，在当前图讲清主要过程、重要条件、状态变化、交接与结果使用。能连贯一起读懂的环节留在一起，避免把复杂业务压成“发起→得到结果”，再让读者连续进入几层换名字的概述。

多入口、后台事件和不同参与者可以属于同一业务。按真实条件保留它们的联系；不能为了得到一条整齐链路，编造共同起止、等待或执行关系。项目里彼此独立的业务则分别安排，不用一张大图容纳所有路线。

### 详图解释需要单独阅读的局部

当局部规则、例外、重复或交叉路径会干扰当前业务讲解，或者需要独立深入比较时，可以单独展开。主图保留该环节具体做什么、关键交接与影响结果的条件，详图提供新的解释。进入后只重复概括、主要内容还在更深一层，说明需要重新整理。

分成平级图与展开局部详图是两个不同选择。独立业务直接并列，不必先做成另一个业务的子节点；同一业务内部的主要环节也不因有独立方法、名称或概念就自动下沉。

图可以大，也可以只有两三步。节点数、固定层数与适应一屏不决定边界。阅读时应能找到业务内容、看清路径；放大平移可以支持较大的连贯流程，不能成为把无关业务堆到一起的理由。先检查边界与内容，再判断是否确有布局或格式能力缺口。

## 5. 写清动作、判断和连接

连线说明已核实的业务先后或条件后续，包含真实用户操作、后台事件与业务交接。业务路径可以跨多次请求；多个入口允许用户带着已有身份、权益或资料直接进入后续。画出完整旅程不表示每次都要重新建立所有前提。

条件应来自业务，不能只为连接本来独立的路线增加“本次选择什么业务”的路由节点。资料归属、分类和纯依赖留在概念关系或业务说明，不冒充执行顺序。确实需要但当前格式表达不了的联系，说明缺什么及其影响。

节点用完整动作和具体对象命名。判断写清：

| 要素 | 需要说明什么 |
| --- | --- |
| 对象与范围 | 一条帖子、一个账号、一个来源路线还是整轮任务 |
| 成立条件 | 全部或任意条件，未知、等于边界时怎样处理 |
| 生效时点 | 保存前判断，还是保存当前页后控制下次请求 |
| 后续与停止 | 继续哪一步、停止哪个对象，已有资料如何处理 |

例如条数和页数两个上限任意达到就停止，直接写明“任一上限达到后结束本路线”，并说明当前页是否保存。“去重”写清判重字段，例如“平台和帖子 ID 相同，沿用已有记录”。

数量、时间、缓存、资格、费用、权限、失败和恢复只在影响当前业务结果时出现，注明作用范围与单位。不要把运行中或失败的路径无条件接到成功结果使用，也不要把受理、付款、交付和最终送达混成同一个状态。

## 6. 用备注说明业务规则的背景

节点与分支说明发生什么，备注补充读者判断合理性所需的业务目的、取舍与依据。已有决定、当前实现和有证据支持的解释分别表明状态；没有来源的理由不写成已确认设计。

采用业务人员使用的称呼，必要术语首次出现时讲清含义。源码文件、类与方法保留给 AI 和 CLI；代码项目归属、状态枚举、调查过程及 AI 为什么这样安排图不进入业务说明。

## 7. 随业务变化维护相关图

行为变化时，在代码所在分支同步受影响的图、条件、备注、摘要和来源。仅源码位置变化修锚点；局部规则变化检查所属图和直接提到它的说明；入口、结果或协作变化再核对相关图；边界变化可以重组平级图与详图。

复用仍然准确的业务身份和事实，清除被新证据否定的关系，不为保留旧层级继续加封面。保留事实不等于保留每张旧图；没有独立阅读价值的实现细节，可以保留概念与锚点供 AI 查询，无需继续作为流程图或顶层入口。合并或重放后按最终源码检查条件、顺序、交接和两边行为叠加；文本无冲突不证明业务自洽。

## 8. 从实际阅读路径验收

1. 重新打开交付入口，查看默认图和顶层选择，确认业务范围与本次任务相符。多个顶层业务分别验收，不要求先展示一张全项目图。
2. 先检查图的边界：相关主线有没有被拆散，无关业务有没有被强行合并，父子关系是否确实提供深入解释。
3. 代入给新同事讲业务的主讲人，仅凭所选图和业务备注讲清该业务的动作、重要条件、状态与交接。必要主线缺失就补回，独立业务切换到对应平级图，复杂局部再进入详图。
4. 走主要路径、关键分支、退出和恢复，核对数量、时间与权限边界。检查实际阅读比例下的文字、连线和条件，不只看缩略图。
5. 检查平级切换、必要的详图进入和返回；详图应增加有用信息。节点角标进入，正文有备注时查看说明。
6. 核对完整文件差异与来源，结构校验、源码事实和实际阅读分别报告。软件能力足够而内容组织有误时，先纠正组织，不把问题转为新增产品功能。

在新上下文检查指导效果时，作者只接收自然业务任务，方法来自已安装 Skill。验收者检查产物与证据，将问题交作者修正，不代画后再声称指导独立成功。达到本次已确认范围后交付，留下具体缺口和实际状态。
