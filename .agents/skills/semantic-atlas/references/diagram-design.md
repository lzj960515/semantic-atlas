# 按业务组织可讲解的流程图

在新建、重画或重组业务图，以及读者看不懂现有图时读取本指南。软件提供文件、管理、搜索、渲染和导航能力；AI 根据业务证据决定画什么、怎样连接、哪些内容放在一起。这里提供判断方法，不规定业务模板、图数、层数或固定节点。

一组业务图可以从多张平级图开始。项目是资料的保存和查询范围，不天然是一个完整业务，也不要求有一张覆盖全部功能的“业务全貌”图。先确定要讲的业务，再确定每张图的范围和必要的深入入口。

业务责任按[业务边界](boundary-design.md)核实，文件和工具按[编写约定](map-authoring.md)使用。归属、共享资料和源码位置帮助调查，不自动产生流程箭头或父子图。

## 1. 从读者要理解的业务开始

明确本次要让读者理解什么业务、作出什么判断，以及哪些事实会影响判断。先从已确认流程与业务决定明确应有行为，再用源码与运行证据核对实现，说明谁做什么、对象怎样变化、什么条件改变路径、结果交给谁使用。

首次建图形成可讨论候选，发现实现没有兑现的保证时，保留业务语义并在备注及维护记录说明差异。图的确认依据来自任务、产品决定和已有评审，不增设逐节点审批；尚未明确的业务取舍标明待定，不能只凭代码存在将其确立为正确规则。

使用具体业务语言。宏观节点可以概括复杂动作，但读者仍应知道发生了什么。例如“顾客下单并付款 → 仓库按订单发货”可以讲业务；“业务触发 → 选择结果 → 返回处理结果”只是一副任意请求都能套用的架子。接收、判断、返回可以是实际业务，写出它们接收什么、按什么判断、改变什么结果。

把当前实现、已经确认的业务要求、用途解释和资料缺口分清。会改变结论的未知先核实；没有依据的业务原因或使用方不写成事实。

## 2. 分块调查并持续修正已画流程

图是可持续修正的外部记忆。首次建图或重建时，从当前能核实的一条用户路径、规则或生命周期开始，读取入口、决定性方法和必要使用方；已有足够证据就及时保存，不等读完全部仓库。

1. 写下当前已经核实的动作、关键条件、结果与源码锚点，核对局部引用。
2. 继续调查会改变这段理解的其他写入方、回调、恢复入口、退出路径或消费者。
3. 新证据否定原来的条件、顺序、归属或边界时，立即修改、删除或重组已画内容，同时检查受影响的摘要、图间引用和备注。不能只追加新节点保留旧误解。
4. 按业务理解继续下一块。分块大小由证据与业务决定，不固定文件数、调查轮数或节点数。

例如先读到“创建订单后调用发货”，后来确认发货由支付成功事件触发，应改回已有路径和发货入口，不能保留原串行关系再加一条支付线。

长任务在所属项目 `tmp/` 保留目标、确认事实、待核实范围、已改流程与下一处源码入口。重要分块或理解变化后更新；恢复上下文先读状态和当前差异。稳定业务知识留在图与所属文档，调查过程不进入业务 UI。

## 3. 分别确定业务边界和图的边界

业务边界由结果承诺、规则和状态的所有权及生命周期决定。图的边界由需要一起理解的业务内容决定，两者不必一一对应：一条客户旅程可以跨多个所有者，一个复杂业务也可以有多张图。

先说清谁要完成什么业务目标、依赖哪些对象，以及得到的结果怎样被使用，再决定哪些内容需要一起讲。单个动作有输入、输出或独立接口，只说明它可以被调用；继续向前看为何做、为谁做，向后看谁怎样使用结果，才能判断它是否适合独立成图。关联的配置、运行、结果使用和恢复不能因分在不同方法、角色、模块或仓库，就画成互不相关的接口碎片。

再检查被放在一起的内容是否有共同的讲解任务。若讲完其中一段就需要切换到另一项独立业务，其余部分对理解前一段没有作用，可以分别成图，放在同一层选择。它们同属一个项目、都使用 AI、共享账号或公共资料，不构成合为一张图的理由。

业务缺少入口、事件或结果使用方时，按缺口继续找证据。缺用户操作就查前端，缺触发就查事件生产者，缺产物去向就查消费者。可访问的相关项目继续调查；第三方内部或不可访问部分保留已知契约和具体缺口，不在仓库边界截断已能查明的业务。

## 4. 根据理解成本安排层次

### 平级图各自讲清业务

独立业务可以各有一张或几张完整图，直接作为顶层入口。顶层不是必须汇总全部图的父图；默认打开其中一张，只是阅读器的初始选择，不要求该图代表全项目。

项目级整理先逐个审视顶层选择项。它应帮助业务人员选择要理解的目标或生命周期，能回答“谁为什么做这些事，最终得到什么”；不能只是把接口或按钮清单搬进目录。管理员操作、后台任务和小工具也要追踪它服务的目标，解释对象、前提与后续用途。需要局部规则时保留详图；简单实现细节可以只保留概念与锚点，但业务目标成立所需的用户或运营过程仍要在相应流程中说清。删除零碎顶层入口不等于这些业务已经整合：如果关键参与者或结果用途只在末尾备注中被点名，读者仍找不到它如何参与，就继续重组主线与交接。不要仅为保留旧图让它占一个顶层入口，也不要仅为减少入口把必要业务藏起来。

再检查这组图是否覆盖指定范围，以及每张图是否讲清它声称的业务。多个独立业务可以平级选择，不必先经过统一封面。只有实际内容适合一起讲时才写更大的主图；它也按业务决定范围，不承担装下全项目的义务。

### 同一业务保留必要主线

对已经选定的业务，在当前图讲清主要过程、重要条件、状态变化、交接与结果使用。能连贯一起读懂的环节留在一起，避免把复杂业务压成“发起→得到结果”，再让读者连续进入几层换名字的概述。

多入口、后台事件和不同参与者可以属于同一业务。按真实条件保留它们的联系；不能为了得到一条整齐链路，编造共同起止、等待或执行关系。项目里彼此独立的业务则分别安排，不用一张大图容纳所有路线。

### 详图解释需要单独阅读的局部

当局部规则、例外、重复或交叉路径会干扰当前业务讲解，或者需要独立深入比较时，可以单独展开。主图保留该环节具体做什么、关键交接与影响结果的条件，详图提供新的解释。进入后只重复概括、主要内容还在更深一层，说明需要重新整理。

分成平级图与展开局部详图是两个不同选择。独立业务直接并列，不必先做成另一个业务的子节点；同一业务内部的主要环节也不因有独立方法、名称或概念就自动下沉。

图可以大，也可以只有两三步。节点数、固定层数与适应一屏不决定边界。阅读时应能找到业务内容、看清路径；放大平移可以支持较大的连贯流程，不能成为把无关业务堆到一起的理由。先检查边界与内容，再判断是否确有布局或格式能力缺口。

## 5. 写清动作、判断和连接

连线说明已核实的业务先后或条件后续，包含真实用户操作、后台事件与业务交接。业务路径可以跨多次请求；多个入口允许用户带着已有身份、权益或资料直接进入后续。画出完整旅程不表示每次都要重新建立所有前提。

条件应来自业务，不能只为连接本来独立的路线增加“本次选择什么业务”的路由节点。资料归属、分类和纯依赖留在概念关系或业务说明，不冒充执行顺序。确实需要但当前格式表达不了的联系，说明缺什么及其影响。

节点用完整动作和具体对象命名。判断写清：

| 要素 | 需要说明什么 |
| --- | --- |
| 对象与范围 | 一条帖子、一个账号、一个来源路线还是整轮任务 |
| 成立条件 | 全部或任意条件，未知、等于边界时怎样处理 |
| 生效时点 | 保存前判断，还是保存当前页后控制下次请求 |
| 后续与停止 | 继续哪一步、停止哪个对象，已有资料如何处理 |

例如条数和页数两个上限任意达到就停止，直接写明“任一上限达到后结束本路线”，并说明当前页是否保存。“去重”写清判重字段，例如“平台和帖子 ID 相同，沿用已有记录”。

数量、时间、缓存、资格、费用、权限、失败和恢复只在影响当前业务结果时出现，注明作用范围与单位。不要把运行中或失败的路径无条件接到成功结果使用，也不要把受理、付款、交付和最终送达混成同一个状态。

## 6. 分清节点简述和详情

节点让人沿图理解业务，详情提供按需阅读的解释。标题用一句话概括具体动作或判断，
优先控制在 24 个中文字内；可见补充优先控制在 40 字内，只补理解这一步或选择分支
所必需的信息。数字是写作预算，英文名称结合实际显示宽度判断，不做机械截断或
文件校验限制。超出时先重写并重新分配正文与详情；关键含义确实无法压缩时可以
适当超出，不能为凑字数省掉对象、动作或决定路径的条件。

仅阅读节点和分支，仍应知道发生什么、正在判断哪件事，以及不同答案怎样继续。
“需要的权限”“符合相关条件”没有说明用途，应写清读取文件、创建文档等具体能力；
较长的权限清单、阈值对照表、计算举例、业务背景和例外放入该节点的 `notes`。影响当前分支
选择的关键条件仍需在节点或分支中可见，不能全部藏到详情。若不同条件会导致不同
后续，按业务需要分开判断，不把多个决定压成一句含糊的“是否可用”。

备注只补一项阅读正文后仍需了解的业务信息，通常一两句。必须逐项核对的权限或阈值
可用短清单。写完后删去重复内容和开发过程，只留下读者会用到的事实。已有决定、
当前实现和有证据支持的解释分别表明状态。有备注时点击节点正文打开详情，点击
子流程角标进入另一张图。

采用业务人员使用的称呼，必要术语首次出现时讲清含义。句子应能说清谁做什么、处理什么对象、发生什么结果；判断应让读者知道正在判断哪件事以及不同答案会怎样继续。内部参数、状态标记和技术名词不能直接拼成节点名称，再让读者猜它的意思。写完后逐句用日常语言复述，复述仍依赖“本次、有效、受理、目标”等未说清的指代时，回到实际对象和动作重写，而不是只替换几个近义词。

标题表达读者要了解的业务，节点写主要动作和条件，备注补必要背景和例外。不要把多项没有先后联系的事实塞进同一句摘要；也不能为了口语化丢掉权限、时间、费用和失败边界。源码文件、类与方法保留给 AI 和 CLI；项目代号、状态枚举、调查过程及 AI 为什么这样安排图不进入业务说明。

## 7. 随业务变化维护相关图

业务变化先在图中表达新规则，再同分支实现，维护相关条件、备注、摘要和来源。实现违背正确流程时修代码并记录差异，不降低图中的业务要求。仅源码位置变化修锚点；局部规则变化检查所属图和直接提到它的说明；入口、结果或协作变化再核对相关图；边界变化可以重组平级图与详图。

复用仍然准确的业务身份和事实，清除被新证据否定的关系，不为保留旧层级继续加封面。保留事实不等于保留每张旧图；没有独立阅读价值的实现细节，可以保留概念与锚点供 AI 查询，无需继续作为流程图或顶层入口。合并或重放先确定共同生效的业务流程，再核对最终代码中的条件、顺序与交接；文本无冲突不证明业务自洽。

## 8. 先审流程源文件，再核对呈现

作者在写完一段流程后主动复盘；新证据改变理解时立即重构已画部分。交付前再从头审查整组流程源文件。自审不是把“已验证”写进报告，而是按下列问题检查实际节点、连接、规则和业务代码，修正后重走受影响路径。

### 先看整组图是否围绕业务目标

逐项读取实际顶层目录及其流程，不以原目录为正确答案。说明每项服务谁、为何发生、怎样使用结果，并核对其他图是否已经在讲同一个目标。内部步骤错成独立业务时合回所属目标；多项独立业务挤在一张图时重新分开。既不为减少目录而编造统一流程，也不因操作可单独调用就拆成碎片。

代入向新同事讲业务的主讲人，仅用流程源文件中的业务标题、节点和备注讲一遍。需要另补关键过程或猜对象用途，说明内容尚不完整；能用具体用户行为和结果讲明白，才说明当前范围成立。

### 再检查每张图的路径与联系

从 `startsAt`、`steps` 和 `transitions` 直接检查孤立节点、互不连接的片段、进入点、条件、结束与恢复。可以用只读图算法列出弱连通分量，帮助发现遗漏；数量只是调查线索，不自动决定画法或判错。

存在多个片段时，逐块核实它与当前业务的真实联系。若它应在某个条件、配置生效点、后台完成或结果使用之后发生，核实并补清这项联系；若它承担另一个需要单独理解的过程，就放到相应图或详图。不能仅凭摆在同一画布、同属一个领域或备注提到它，就让读者自行拼接。也不能为通过连通检查画出不成立的先后、共同入口、等待或成功结果。

沿每个真实入口走到结果，检查主要条件、并行交接、失败、停止和恢复对象。配置改变影响下一次运行时写清生效时点；即时影响与下次生效分别表达。用户随时查看结果不表示必须等所有后台工作结束，入口和阅读关系按事实说明。

### 核对措辞与事实，再看渲染

逐句读标题、动作、判断、分支和备注，确认正常业务人员不需要源码词汇也能理解主体、对象和结果。先只读节点与分支讲一遍，确认不用打开每个详情也能理解路径；再检查细节是否放在相应备注，关键条件是否因压缩而丢失。用自然中文重述仍说不清，就回到业务行为重写。用业务代码核对权限、时间、数量、费用和失败传播，不把清楚好读当作事实正确的证明。

逻辑与表达审查主要在源文件完成。网页或导出用于检查渲染后的布局、线条、文字显示，以及必要的进入和返回；不替代源文件审查，也不要求每次逐页打开。结构校验、源码事实、语义自审和呈现检查分别报告。

### 独立审查与返修

整体重整或修正画法后，由另一个上下文检查实际产物与来源，先看业务目标、完整路径和人能否读懂，再看格式和锚点。作者只接收自然业务任务，方法来自 Skill；预期答案留在验收端。验收者不代画后声称指导独立成功。

发现问题时先判断是局部误写，还是划分、语言或审查方法有误。后一类要回看全部受影响产物并重组；不能只修读者圈出的节点，继续保留同类错误。指导与旧产物冲突时先修指导，再重新检查结果。达到本次已确认范围后结束，交代实际证据及仍缺少的来源。
