# 业务边界判断

创建或改变业务划分，或某个所有者、生命周期与协作者可能改变工程结论时读取。本页负责判断业务责任；[文件编写](map-authoring.md)负责表达。按当前范围使用：项目请求核对其业务及必要协作，局部请求核对完整邻域，普通工程任务只建立足以决定改动的模型。代码仓库与业务边界分别判断。

## 先确定责任，再安排流程

一个业务范围承诺一个可理解的结果，拥有让结果成立的规则与状态，并解释这些状态如何建立、使用、改变和结束。同一客户旅程可以跨越多个这样的所有者；调用别人、使用同一张表、出现在同一路径，只能证明协作。

从当前分块的证据建立责任判断，再选择所属文件；后续证据可能要求修改已定边界。对这块已经调查的范围回答：

| 问题 | 要取得的证据 |
| --- | --- |
| 谁依赖什么结果？ | 用户、运营者或其他业务可以依赖的承诺 |
| 谁决定规则和状态？ | 权威记录的含义、允许的变化和判断权 |
| 生命周期怎样开始与结束？ | 真实入口、变更、停止、恢复及重要拒绝／失败路径 |
| 与谁交换什么？ | 输入输出、协作契约、外部所有者与当前仓库的限度 |
| 哪里证明这些事实？ | 当前入口、写入方、规则与测试；会改变边界的缺口 |

简短任务可以把判断留在工作说明里，不必新增文档。以上问题用来检验现有责任，不形成没有业务依据的新功能。

## 独立核对覆盖

先从产品承诺和用户／运营入口发现支持的业务，再用旧图核对。检查会改变当前结论的状态写入、配置与权限所有者、事件／任务／回调和重要分支测试。技术目录帮助定位，不能决定业务划分。

边读边补充覆盖记录，分清已证实、未调查和证据不足；不必等全部业务读完才落图。按需保留一张简表：`场景或生命周期 → 所有者 → 决定性证据 → 对应概念／流程，或省略原因`。协作、实现细节和待核实都可以成为明确的省略理由。已经画出某个节点，不证明覆盖完整。

多个等价入口可以共用一个场景和多个锚点。只有动作具有独立业务判断或结果时才单独建场景。方法数量、CRUD 列表和每个接口一张图都不是完成标准。

## 检验划分是否成立

| 可能的问题 | 如何用证据判断 |
| --- | --- |
| 过大 | 是否存在能分别交付结果、各自决定规则和状态的责任？分别保留所有者与协作。 |
| 过碎 | 这些片段是否共同建立、改变或结束同一个结果？保留一个责任，下分能力或场景。 |
| 遗漏 | 独立发现的入口、状态变化或退出路径是否有重要行为却没有所有者？补到相应层，或记录缺口。 |
| 放错位置 | 是否仅因调用、消费或目录相同，就放在某业务下面？按规则与生命周期的实际决定者修正归属。 |

共享概念只定义一次，再表达已确认的读写和调用关系。同一物理表可能承担不同业务含义；同义业务也可能由多个技术模块实现。依业务语义保留身份。

通用执行能力如果独立承诺取消、恢复、完成等生命周期，可以有自己的业务责任；辅助转换、队列包装和适配器的可调用方法，不足以证明独立业务。

## 区分归属与阅读范围

`part_of` 记录业务归属。总览流程可以引用不同所有者的场景，解释真实存在的端到端旅程，但不把被引用的业务改归总览所有。图的范围与层次由实际业务和阅读需要决定；互不相连的业务保持独立路径，分类与导航不构成执行流程。具体表达见[流程设计](diagram-design.md)。

业务旅程缺少用户入口、前置事件、状态所有者或结果使用方时，按这些缺口定位其他仓库，
读取前端页面、调用方、生产者与消费者，补齐整体叙述。源码分在几个项目，不决定业务
该拆成几张图，也不证明当前仓库里的半段流程已经自洽。业务资料的维护归属与证据所在
项目分别记录；不因一张图包含跨项目协作而改变实际业务所有者。

相关项目可读取时沿业务路径继续核实，不把“跨仓库”当成停止调查的理由。第三方或
不可访问部分按已确认接口和必要交接表达，并保留具体缺口，不编造其内部实现。

## 何时结束

当前分块拥有可证实的结果、规则或状态，重要路径及协作在证据边界内可解释时，及时编码为概念和流程，保留仍准确的稳定 ID，继续下一处必要调查。新证据揭示归属错误、遗漏或跨业务交接时，回头重构已画部分，具体方法见[持续建图](diagram-design.md#2-分块调查并持续修正已画流程)。

不确定性会改变归属时，明确记录并只推进有依据的部分。工程调查在行为、所有者和必要协作已足以决定本次改动时结束；画图任务在指定范围的覆盖与完整路径可解释时结束。结构校验和可读性都不能替代业务判断。
