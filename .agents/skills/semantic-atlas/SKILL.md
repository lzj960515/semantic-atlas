# Semantic Atlas

让人和 AI 围绕同一份业务流程协作。AI 理解当前业务、核实实现、编写和维护文件；人通过只读界面选图、阅读、按需深入和讨论。所有图统一使用业务流程图。

软件负责管理、组织、搜索和渲染业务资料，提供文件约定、使用方法与画图的最佳实践。
具体画什么、业务边界在哪里、怎样概括、拆分和连接，由 AI 根据实际业务与阅读需要
自主判断。本 Skill 帮助 AI 作出这些判断，不预设通用业务框架或固定画法。

按实际业务决定每张图的边界。独立业务可以直接成为多张平级的顶层图，无需共同父图，
也不要求专门画一张“业务全貌”。默认打开哪张只是阅读器的选择，不要求它覆盖项目。
选定一段业务后，在图中讲清连贯的主要过程、重要条件、交接和结果；复杂局部再按
阅读需要进入详图。既不把一条业务拆成层层封面，也不把无关业务堆进同一画布。
图数、节点数和层数由内容决定。业务跨前端、后端或其他项目时，沿缺失环节找源码，
资料的保存位置不截断业务范围。验收要看实际默认入口、平级选择与必要的深入阅读。

业务图提供调查线索。当前源码、测试、已跟踪的产品决定和必要的运行证据，决定这次可以作出的结论和改动。业务行为变化时，代码与相关流程在同一分支修改、审阅和提交合入。没有业务变化时，不为代码内部调整重画流程。

## 1. 从任务确定工作范围

| 当前请求 | 本次应完成什么 |
| --- | --- |
| 功能、缺陷或重构 | 理解受影响业务，核实证据；行为变化时同步实现和相关流程，检查两者一致 |
| 评审或影响分析 | 对照当前源码与流程判断影响；用户仅授权分析时，报告必要修改而不直接写文件 |
| 新建、修改或重组流程图 | 完成指定业务范围的调查、流程文件和实际阅读检查 |
| 已明确源边界的格式化、局部改名等机械任务 | 直接按仓库工作流完成；业务含义保持时不改流程 |
| 用户明确要求处理历史观察或候选 | 使用文末可选历史工具，不改变正常工程的同步维护方式 |

普通工程任务不意味着重画整个仓库。是否提交、合入、发布或改变数据结构，遵循本次授权和仓库规则；同步代码与图表示一个完整候选，不自动取得发布或生产操作授权。

## 2. 直接定位相关业务与源码

根据任务、工作空间的项目映射和 `AGENTS.md` 确定业务资料的维护位置和调查起点，当前工作目录不一定是目标仓库。仓库用于定位证据，不限定业务范围；根据流程缺少的入口、事件、状态写入或结果使用方，继续定位相关项目。已登记项目优先用 `--project "<name-or-id>"` 查询；已知名称或 ID 时可以直接使用，需要核对时运行 `semantic-atlas project list`，查看 `id`、`name`、`displayName` 和 `repositoryPath`。名称取登记路径的目录名，按大小写、Unicode NFKC 和首尾空白归一后精确匹配；重名时用列表中的 ID 明确选择。

`PROJECT_NOT_FOUND` 的相近项目仅是建议，`PROJECT_AMBIGUOUS` 的候选需要消歧。结合任务与 `repositoryPath` 判断目标，再用确切名称或 ID 重试；不能把短名、误拼或第一个候选当成已选中项目。未登记或已有确切路径时，用 `--repo "<目标仓库绝对路径>"`；`--project` 与显式 `--repo` 互斥。查询、校验、渲染和 Web 均可按项目选择，源码锚点始终相对选中仓库解析。CLI 不递归发现子仓库的业务图，多仓库任务分别查询，不能用错误根目录的 `MAP_NOT_FOUND` 判断子仓库没有图。

确定目标后，从已经掌握的信息进入相关业务。AI 可以像熟悉系统的程序员一样直达目标，不必每次从总览走完整层级；人的级联浏览菜单不规定 AI 的调查顺序。

| 已有信息 | 直接入口 |
| --- | --- |
| 已知流程 ID | `semantic-atlas flows "<flow-id>" --project "<name-or-id>"` |
| 已知业务概念 ID | `semantic-atlas context "<concept-id>" --project "<name-or-id>"` |
| 只有要完成的业务行为 | `semantic-atlas search --flows "<business-query>" --project "<name-or-id>"`，先判断候选与随附关联，再按需读取流程 |
| 需要补看整体结构或没有合适命中 | 可选用 `semantic-atlas flows --project "<name-or-id>"` 取得根流程与简要目录 |

表中示例选择已登记项目；按路径查询时，将该选项替换为 `--repo "<repository-root>"`。

查询返回紧凑 JSON，`repository.root` 确认资料与本地锚点所属仓库，不列全库文件。
搜索保留最多五个候选，每个命中带维护位置；随附业务摘要只属于 `contextFor` 指定的
第一候选，帮助判断入口，不表示它已被选定。先结合业务含义核对候选；另一个候选更
合适时，按其概念 ID 调用 `context`，或按流程 ID 调用 `flows`，取得对应资料。

摘要中的 `concepts` 按 ID 唯一提供业务含义、规则、备注与源码锚点；`relations` 用
`from`、`type`、`to` 和 `summary` 说明关联原因；`flows` 列出所属场景或步骤引用，
`references` 指明引用概念、步骤及位置。这些条目的 `map.file/line/column` 定位当前
YAML 中应维护的声明。`scope: "recorded"` 表示只反映已记录关系：直接关联与共享数据、
接口、规则的其他使用方可提示要检查的业务及图，不能据此认定全部影响或排除未记录
的消费者。结合当前源码判断哪些图确实需要同步，不因有关联就全部改动。

需要完整动作、判断、条件和结果时再读 `flows <flow-id>`。其 `selected` 提供本层
步骤与转换，`scenario`、`parents`、`steps[].concept` 和 `steps[].childFlows` 用 ID 引用；
概念的详情从同一响应 `concepts` 查。`context` 的所选概念单独在 `selected`，其余
概念在 `concepts`。当前资料已足以确定入口时直接核实对应源码；只有上层承诺、细节
或必要协作会改变结论时，才补看父层、子流程或另一个概念，不展开无关邻域。

`search --flows` 根据流程及相关业务文本的词面相似度返回候选，不是向量或语义搜索。不同词汇、同义改写或不同语言可能没有命中；分数只说明这次查询的相关排序。需要概念检索时可用普通 `semantic-atlas search "<business-term>"`，同样按业务含义判断结果，而不是把分数当正确性证明。

符号锚点用 `file` 定位文件，再查 `value` 指定的类、方法或函数；它的
`resolution: "hint"` 不代表已定位声明行。`missing` 表示预期本地路径缺失或类型不符，
应查当前替代入口；文件／文档锚点的 `located` 仅指向文件开头。YAML 维护行号从本次
文件派生，不能当成代码行号。打开当前声明和必要调用方，确认实际动作；资料仍是导航
与规则线索。

| 结果 | 怎样继续 |
| --- | --- |
| 取得相关流程或概念 | 核实当前图的规则、源码和必要使用方，不强制补走总览 |
| 搜索为空或存在歧义 | 使用已知业务词、可选目录或源码入口继续调查；会改变范围且仍无法确定的选择保持待核实 |
| 项目未找到或项目名称重名 | 核对候选与登记目录，明确项目后再查询；这是项目选择结果，不说明该仓库缺少业务图 |
| 没有相关流程或 `MAP_NOT_FOUND` | 建立当前任务所需的最小业务模型；行为变更时补写相关流程，不先建完整分类体系 |
| 流程 ID 不存在 | 按当前目录和源码核对替代路径 |
| 文件无效或 CLI 不可用 | 说明资料不可用，继续有界源码调查；能在本次范围修正的资料问题一起处理 |
| 锚点缺失或过期 | 用当前实现找到替代入口，同步修正本次依赖的锚点，保留其他仍成立的业务知识 |

核实谁承诺结果、拥有规则与状态，谁是调用者或协作者。边界不清或需要调整业务资料时，读取[业务边界](references/boundary-design.md)。沿真实生产者、使用方和外部交接确定影响，不以目录或类数量代替业务责任。

## 3. 同步修改实现与受影响流程

从相关流程的起点走到本次可能影响的结果，核对动作、判断、条件分支、停止和恢复对象。重点确认会影响数据、费用、权限、租户隔离、接口和用户结果的路径，只追踪当前任务所需范围。

先区分差异的含义：实现违反已确认规则时修代码，并让图准确表达修复后的支持路径；业务要求改变时同步改代码和流程；源码位置变化时修正必要锚点；仅内部组织变化且业务含义不变时，保留流程。证据冲突且会改变行为时，先确认关键决定。

代码修改与相应流程文件放在同一工作分支。局部条件只改所属细图和直接提到它的说明；入口、结果、重要分支或协作变化时，再检查引用它的上层与相关协作者。不要把必要的图更新留成候选，等合入主分支后才维护。

按仓库工程工作流验证并审阅完整差异，把代码行为和图中的规则、分支、备注与源码锚点一起检查。没有业务变化，或图已完整表达修复后行为时，可以没有结构性图修改，但应说明核对结果。

## 4. 编写流程资料

首次建图或重建较大业务范围时，边分块读取源码边画，不等读完整仓库才写图。按照[流程设计中的持续建图方法](references/diagram-design.md#2-分块调查并持续修正已画流程)，把已核实的局部流程及时落盘，记录未覆盖范围；后续证据改变理解时，立即修正或重构已画部分，再继续调查。图和必要状态文件承载外部记忆，当前源码仍负责证实行为。

项目初始化或整体重整，将已核实的内容按业务组织为可讲解的平级图及必要详图，
检查指定范围是否覆盖、各业务主线是否完整；不强制增加全项目汇总图。局部工程
任务只更新受影响的图。AI 查代码可直接定位相关业务，不必从顶层逐层走。

新建图、修图或同步行为变化时：

1. 按[业务边界](references/boundary-design.md)建立当前分块有证据的责任范围与必要协作者，逐块核对源码入口、状态和规则，并随新证据修正边界与已画流程；旧节点列表不构成完整性证明。
2. 按[流程设计](references/diagram-design.md)决定哪些内容共同说明一段业务，哪些是独立的平级业务，哪些局部需要详图。每张图使用具体动作、判断与结果讲清自己的业务；相关主线保持连贯，独立业务分别安排，不为统一入口编造共同触发或执行关系。
3. 按[文件编写](references/map-authoring.md)使用当前产品格式。复用仍成立的业务身份，共享概念只定义一次。`part_of` 表达归属，不产生执行顺序；各图由 AI 按真实业务显式编写为 `flows`，需要详图时通过步骤的 `concept` 引用场景的自有流程。
4. 同一业务责任仍成立时复用其文件；独立新业务有自己的领域和文件。文件数量由真实责任决定。新版格式需要更好的表达时，可以按已确认契约重写既有资料，无需为旧业务文件或旧格式保留兼容分支。
5. 源码锚点保留到具体文件、类和方法，供 AI 与 CLI 定位；Web 隐藏这些资料。备注说明业务规则的背景、目的和取舍，不写 AI 怎样安排图的理由。
6. 完成结构与阅读检查：

   ```sh
   semantic-atlas validate --repo "<absolute-repository-root>"
   semantic-atlas render --repo "<absolute-repository-root>" --output "<repository-root>/tmp/business-flow.html"
   git diff --check
   git diff -- docs/business-map/
   ```

   从交付入口重新打开，检查默认图、平级业务选择与本次覆盖范围。先核对有没有
   拆散相关主线或强行合并独立业务，再代入主讲人，用每张图和备注讲清它自己的业务。
   缺失的必要过程补回对应图；其他业务切换平级图，复杂局部进入详图。核对关键分支、
   时间与数量边界、进入和返回，以及实际阅读比例下的文字和连线。角标直接进入
   子流程；节点正文仅在有业务备注时打开说明。

结构校验证明文件与引用有效，源码证据证明行为，实际阅读证明表达清楚；三者不能互相替代。

## 5. 合并时按最终行为消除冲突

代码与流程图作为同一业务变更提交和合入。审查通过后，按当前授权执行仓库的提交或合并流程；只有本地修改时如实报告候选状态。

遇到分支合并或重放冲突，先理解两边各自改变的规则、入口、结果和协作，再按合并后的代码重审受影响流程。即使文本没有冲突，也要检查两项行为变化叠加后，分支条件、顺序、子流程引用和备注是否仍然成立。不能仅保留两边文字或按格式拼接 YAML。

解决后重跑受影响的业务验证、完整图校验和必要阅读检查，确保合并结果中的实现与流程一致。未取得业务决定或关键证据时，保留具体阻塞，不用测试断言替代决定。

## 6. 可选：已有历史记录

正常工程不要求先生成候选、记录观察或等待主分支更新。只有用户明确要求准确性记录，或要处理已有历史观察和候选时，才读取[观察记录](references/observations.md)与[历史候选校准](references/reconciliation.md)，使用已有 `observe`、`reconcile` 命令。它们不替代本次同分支维护，也不阻断代码与流程的交付。

## 7. 交付

说明当前业务边界、关键依据、代码与流程分别改了什么，以及实际验证。没有业务变化或无需结构性改图时给出简短依据。直接画图提供阅读入口与文件；仅分析时说明建议改动。把已核实的覆盖、尚未调查的范围、资料缺口、未完成的运行验证，以及本地修改与实际合入状态分别讲清楚。当前结果已充分验证后结束，不补画无关业务。
